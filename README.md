# Мини-CRM «Объекты и задачи»

React + TypeScript + Supabase: постановщик управляет стройками и задачами, исполнитель работает с назначенными ему задачами. Данные демонстрационные.

Локальные функции и интеграция проверены. Облачная публикация пока не завершена; рабочего публичного URL ещё нет.

## Запуск

Нужны Node.js 22.12+ и отдельный Supabase-проект.

```sh
npm ci
```

Скопировать `.env.example` в `.env.local`, заполнить URL проекта и публичный publishable/anon key. Никогда не использовать service_role или secret key в VITE-переменных: они доступны браузеру.

В облачном Supabase:

1. Отключить открытую регистрацию в Auth.
2. Применить файлы `supabase/migrations` по порядку: 001 → 002 → 003.
3. Вручную создать подтверждённых email/password-пользователей `crm.manager@example.com`, `crm.executor.a@example.com`, `crm.executor.b@example.com`, задать разные случайные пароли.
4. Один раз выполнить `supabase/seed.sql`: он создаёт роли, два вымышленных объекта и пять задач в разных статусах. Seed рассчитан только на отдельную пустую тестовую базу.

```sh
npm run dev
npm run build
```

Локальный адрес — http://127.0.0.1:4376. Production-файлы — в `dist`. Навигация через hash; SPA rewrite не нужен. В Netlify задать две публичные VITE-переменные и собирать `dist` через включённый `netlify.toml`. Сборку с loopback API URL не публиковать.

## Что реализовано

- Вход по email/паролю, две роли с несколькими пользователями.
- Объекты, задачи, создание/редактирование/удаление, перенос задач и переназначение.
- Новая → в работе → на проверке → принята либо на доработке → в работе.
- Обязательный комментарий при возврате, история создания и переходов.
- RLS ограничивает чтение; RPC в базе проверяют права на изменение. Прямые записи в таблицы с клиента запрещены.
- Смена статуса и история атомарны. Блокировки и ожидаемые значения защищают конкурентные изменения.

Роли задаёт администратор в `profiles`; пользовательские metadata не дают полномочий. Исполнитель не может прочитать чужую задачу, принять свою работу, изменить поля или историю. После переназначения прежний исполнитель теряет серверный доступ, новый получает всю историю. При удалении задачи история удаляется вместе с ней.

## Проверки

```sh
npm test
npm run test:browser
```

Основная suite: 20 проверок, включая исполнение миграций в PGlite, отрицательные проверки прав, все 75 сочетаний переходов, атомарный откат и CRUD. `test:browser` использует подменённый API и установленный Google Chrome.

Для настоящих локальных Auth/JWT/REST и браузера без моков нужны Docker и Chrome:

```sh
npm run local:start
npm run test:live
npm run test:live:browser
npm run test:live:reliability
npm run test:live:proxy
npm run local:preview
```

Тестовый compose изолирован; Auth/REST публикуются только на 127.0.0.1, порт PostgreSQL не публикуется. Локальные тесты прошли: 14 API-групп, 12 browser-групп, 3 reliability и 5 proxy-проверок. Это не доказательство настроек конкретного облачного проекта: после публикации повторить внешние проверки.

`test:live` создаёт только вымышленные локальные аккаунты и локальные env/credential-файлы, исключённые из Git и HTTP-выдачи. `tests/live/bootstrap.sql` и `auth-helpers.sql` относятся только к тестовой платформе; в облаке их не выполнять. Остановка без удаления данных:

```sh
docker compose --env-file tests/live/.env.local -f tests/live/compose.yml stop
```
